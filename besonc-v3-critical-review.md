> **Purpose:** Honest, evidence-based critique of `besonc-v3-plan.md` after a deep re-read and online research into Paystack, Google Maps, Hubtel, Smile ID, Glovo, Uber Eats, DoorDash, Deliveroo, and Ghana-specific payment / SMS / KYC docs.

> **Format:** Each item has: (a) What's bad/risky, (b) The evidence, (c) A concrete recommendation.

## Detail on the Top 5 Critical Issues

### Issue 1: Paystack Bank Code Names Are Mixed

**What's wrong:** Section 8.1 and Section 16.2 say:
```
Paystack bank codes for Ghana Mobile Money:
- MTN — MTN Mobile Money
- VOD — Telecel (formerly Vodafone) Cash
- ATL — AirtelTigo Money
```

But Paystack's actual docs use **lowercase** for the Charge API `mobile_money.provider` and **uppercase** for the Transfer recipient `bank_code`:

| API | Field | Allowed values |
|---|---|---|
| `POST /charge` | `mobile_money.provider` | `mtn` \| `atl` \| `vod` (lowercase) |
| `POST /transferrecipient` | `bank_code` | `MTN` \| `ATL` \| `VOD` (uppercase) |

Source: https://paystack.com/docs/api/charge/ ("provider: One of: mtn | atl | vod | mpesa | orange | wave | mpesa_offline | mptill") and https://paystack.com/docs/transfers/creating-transfer-recipients/ (the example body literally has `"bank_code": "MTN"` for the recipient).

**Impact:** If we hard-code `MTN/VOD/ATL` and use them in `mobile_money.provider`, the Charge API will reject them. If we hard-code `mtn/vod/atl` and use them in `bank_code`, the Transfer Recipient API will reject them.

**Recommendation:** 
- Two constants:
  ```typescript
  const CHARGE_PROVIDER = { MTN: "mtn", VODAFONE: "vod", AIRTELTIGO: "atl" };
  const TRANSFER_BANK_CODE = { MTN: "MTN", VODAFONE: "VOD", AIRTELTIGO: "ATL" };
  ```
- Add a single translation function `providerToBankCode(provider)` in the Payment Service.

### Issue 2: "Pre-Authorization" via MoMo Does Not Exist

**What's wrong:** Section 8.5 says:
> "When a COD order is placed, the customer's wallet or a payment method is pre-authorized as backup. If the rider reports 'customer refused/unreachable', the system auto-charges the backup."

The assumption is that MoMo supports an "authorize now, capture later" pattern. **It does not.** Paystack's Charge API for MoMo is a one-shot charge — you call it, the customer approves on their phone, the money moves (or doesn't). There is no "hold."

The only "pre-auth" Paystack offers is on **cards** (via authorization codes), not on MoMo. Sources: https://paystack.com/docs/api/charge/ and https://paystack.com/docs/payments/payment-channels/

**Impact:** If the rider arrives and the customer refuses to pay cash, the plan says "auto-charge the backup." But we never got authorization. The only way to make this work is to **charge the customer at order placement** (i.e., require a card or wallet, not MoMo) and refund if COD succeeds. That changes the economics entirely.

**Recommendation:** Two options:

**Option A — Make COD truly cash-only, accept the risk:**
- Customer chooses COD at checkout
- We do not collect any payment at this stage
- If rider reports "customer refused/unreachable," we have no backup; mark the order as failed, customer flagged, no money moved
- This is how Glovo / Deliveroo work in many markets

**Option B — Force a deposit (GHS 10-20) on order placement, refund on successful COD delivery:**
- Customer pays GHS 10-20 deposit via MoMo at order placement
- Rider collects the full COD amount in cash
- If COD succeeds: refund the deposit to wallet
- If COD fails (no customer): keep the deposit, charge the rider's COD liability, customer flagged
- This is how Careem and some Bolt Food markets work

Option B is the better fit for our "Riders never use personal money" rule, because it means the platform has already taken a small bite.

### Issue 3: Paystack Ghana Settlement is T+1, Not Instant

**What's wrong:** Section 9.3 says:
> "Food / groceries / errands — Instant"
> "Order Delivered → earnings available immediately"

But Paystack Ghana's settlement cycle is:
- **T+1 for collections** (next business day for Charge → balance)
- **Transfer fee: GHS 1 per MoMo, GHS 8 per bank**
- **Transfer min GHS 1, max GHS 50,000**

Sources: https://support.paystack.com/en/articles/2123586 (automated payouts) and https://paystack.com/gh/pricing ("Your money is automatically settled to your bank or mobile money account the next working day (T+1)") and https://paystack.com/blog/product/transfers-in-gh (transfer min/max).

**Impact:** The "instant payout" promise breaks in three ways:

1. **Funds from the customer don't land in our Paystack balance until T+1.** If the rider delivers at 6pm today, we can't pay them at 6pm today because we haven't received the customer's money yet.

2. **Each transfer costs GHS 1.** If a rider earns GHS 8 from one order and we transfer immediately, fees eat 12.5% of the earning. That's not viable for high-frequency small payouts.

3. **Daily rider payout volume will hit the GHS 50,000 single transfer limit fast.** In a city of 50 active riders, each earning GHS 500/day = GHS 25,000 just in payouts.

**Recommendation — three layers:**

**Layer 1: Buffered balance.** Operate a "Besonc Operational Balance" — a pre-funded float we maintain at Paystack (or at a Ghana bank account). When a rider requests withdrawal, we transfer from our balance, not from incoming customer funds. This decouples payout from T+1.

**Layer 2: Settlement windows that match reality.**
- Food/Groceries/Errands earnings: "available after settlement" = T+1 from delivery
- "Instant withdrawal" only for riders with cleared balance, capped at GHS 200/day instant, rest goes to T+1 batch
- Daily 10am batch payout for everyone with GHS 50+ available, GHS 0 fee to rider (we absorb)

**Layer 3: Bulk transfer for batch payouts.** Paystack supports up to 100 transfers per batch. Use this for the daily batch. Per-transfer fee of GHS 1 × 100 = GHS 100 per batch, vastly cheaper than 100 individual API calls.

**Layer 4: Re-spec the Section 9 wallet limits.** "New GHS 1,000" is fine, but only as a withdrawal throttle, not as a "we can pay this instantly" guarantee.

### Issue 4: Distance Matrix API Cannot Be Cached

**What's wrong:** Section 6 says:
> "All distances use **road distance via Google Directions API**. Fallback: straight-line × 1.4 (Ghana road winding factor). Routes cached in Redis (24h TTL) for vendor→common-zone patterns to reduce API costs."

This directly violates Google Maps Platform Service Specific Terms Section 1.4(e), which prohibits caching data "to prevent [Google] from tracking your usage for billing."

Sources: https://stackoverflow.com/questions/79923567 (clearly explains the ToS issue) and https://www.lunar.dev/post/a-developers-guide-overcoming-challenges-with-googles-distance-matrix-api (caching for billing evasion is banned; temporary performance caching is fine).

Also, **Google now recommends the Routes API (Compute Route Matrix) over the Distance Matrix API** (legacy since March 2025). Source: https://nicolalazzari.ai/articles/understanding-google-maps-apis-a-comprehensive-guide-to-uses-and-costs

**Cost reality:**
- Distance Matrix: $5 per 1,000 elements
- An element = 1 origin × 1 destination
- 1 dispatch = 1 rider × 1 vendor = 1 element; if we also pre-check 10 alternative riders, that's 10 elements per order
- 500 orders/day × 10 elements = 5,000 elements/day = 150,000/month = $750/month
- At 5,000 orders/day, $7,500/month just for dispatch distance matrix

**Recommendation:**

1. **Drop the "24h route cache" line** from Section 6. Replace with: "Compute route data on demand; cache **Place IDs** indefinitely (this is allowed); no caching of route results."

2. **Switch to Routes API (Compute Route Matrix)** — same $5/1K elements pricing but with traffic-aware ETA, better field masks, and is the path Google is investing in.

3. **Implement the 80% cost reduction pattern:**
   - Use Haversine (straight-line) distance to **pre-filter** to top 10-15 nearest riders before calling Routes API
   - Call Routes API only with the filtered subset
   - For ETA in customer app, call Routes API once per visible order, debounce 30 seconds

4. **Set daily quota in Google Cloud Console** at the free $200-equivalent per month to prevent billing shock.

5. **For ETA estimation, ML-predicted historical averages** (e.g., "from Kotokuraba to Cape Coast Tech Univ on a Saturday at 7pm is on average 18 minutes") can replace many Routes API calls. Train a simple model on the first 3 months of data.

### Issue 5: Internal Double-Entry Ledger is Overkill for v1

**What's wrong:** Section 8.3 specifies a full double-entry ledger with platform accounts, per-user accounts, external accounts, debits/credits. This is essentially a mini-banking-core in our backend.

**The cost of this:**
- A correct double-entry ledger with idempotency, reconciliation, and audit is **3-6 months of senior backend engineer time** alone
- We have 13 microservices, 4 BFFs, observability, saga/outbox/CDC, all to ship in 12 sprints
- The ledger competes with everything else for engineering time

**The benefit of Paystack Subaccounts/Transaction Splits (which we're rejecting):**
- Subaccounts settle vendor payments directly to their bank/MoMo — no ledger needed for vendor payouts
- Transaction Splits divide each customer payment at the moment of charge — no need to "reconcile later"
- The cost is loss of control (subaccount money is at Paystack's T+1, you can't claw it back easily) and the inability to handle complex flows like "wait until rider is assigned, then split"
- The "tricky part" per https://www.mctaba.com/learn/paystack/paystack-split-payments-and-marketplaces-complete-guide: "creating or selecting the right split group dynamically at checkout, and handling cases where the rider has not been assigned yet when the customer pays"

**But our flow has the rider assigned BEFORE the customer pays** in most cases (food is the exception, but even there, we know the vendor's pre-fare estimate). So the "rider not assigned" problem is real for food but not blocking.

**Recommendation — pick a path, not a half-step:**

**Path A — Lean start (recommended for Cape Coast launch):**
- Use a **single `user_balances` table** (user_id, balance, updated_at) — NOT a full ledger
- Every money movement = one row in `user_balances` with audit trail
- The double-entry property is enforced by reconciliation jobs, not at write time
- Migrate to full double-entry ledger in year 2 when you have finance team and audit requirements

**Path B — Full double-entry (current v3.0 plan):**
- Acknowledge the build cost (3-6 months, senior engineer)
- Reduce scope elsewhere (fewer microservices, simpler state machines)
- Pre-launch: have a Ghana fintech lawyer sign off that this isn't a stored-value facility

**Path C — Hybrid (most realistic):**
- Use Paystack Subaccounts **for vendor payouts only** (settle vendor's portion directly to vendor's Paystack subaccount, then transfer to their MoMo)
- Use internal ledger **for rider payouts and customer wallet** (rider flow is more complex, subaccount doesn't fit)
- This means we do use Subaccounts in one place — which contradicts the user's rule, but it's a targeted exception with a clear reason
- **Get user approval before going this route**

I would recommend Path A or C, not B, for Cape Coast launch.

## Smaller but Important Issues

### Issue 6: Device Lock Will Kill Rider Supply in Ghana

Deliveroo UK (June 2025, under UK Home Office pressure) had to introduce **daily facial recognition checks** to combat illegal working via shared accounts. They had to do this because the controls were leaky. Source: https://www.gov.uk/government/news/delivery-firms-to-bolster-rider-security-checks-to-stop-illegal-working and https://lomidriver.com/deliveroo-rider-login

In Ghana, the reality is even more acute: shared phones, family phones, "this is my brother's phone but I'm using it," multiple riders per device.

**Recommendation:**
- Make device lock **soft** — track device fingerprint, allow new device with OTP + admin review (already in our plan)
- Add **"Registered Substitute Rider"** concept (a named individual, KYC'd via Smile ID, who can use a primary rider's account under the primary's supervision, with daily limits)
- This is what Deliveroo UK does legally; it gives us the safety of named KYC'd individuals without forcing every rider to own a smartphone
- Do NOT enforce 1-device-1-rider at launch; add it after 1,000+ riders are onboarded

### Issue 7: "Riders Never Use Personal Money" + GHS 3,000 Cap = Can't Buy Anything

The dev plan says riders never use personal cash for Buy errands. But the same plan caps errands at GHS 3,000 for trusted users. The two together mean: a rider cannot buy anything over a few hundred cedis, even for trusted customers.

We need a **"Besonc Pay" mechanism** — a per-errand payment instrument:

**Option A — Vendor direct billing:**
- Customer's wallet holds the budget
- At checkout, customer pre-authorizes a "purchase allowance" to the vendor's MoMo
- Rider shows vendor a Besonc-generated voucher code (single-use, expiring in 30 min)
- Vendor redeems via SMS or USSD

**Option B — One-time virtual MoMo number:**
- Paystack doesn't support this; but Hubtel's payment platform or MTN's API can issue a virtual MoMo line
- More complex integration

**Option C — Cash advance with limit:**
- Besonc issues a "Cash Advance" to the rider's MoMo up to GHS 200 per shift
- Rider reconciles receipts at end of shift
- This is what Glovo does in some markets

**Recommendation:** For Cape Coast launch, do Option C with a hard GHS 200/errand limit, GHS 500/day limit. Build Option A (vendor voucher) for year 2.

### Issue 8: Transfer Fees Will Eat Margins

Paystack Ghana transfer fees:
- MoMo: GHS 1 per transfer
- Bank: GHS 8 per transfer

If we payout 200 riders/day via individual transfers = GHS 200/day in fees = GHS 6,000/month. If we use bulk transfer (up to 100/batch, 1 call = 100 transfers), it's 2 calls = GHS 200 in Paystack's perspective (each transfer still has GHS 1 fee, but the API call is 1).

**Plus the 1-free-withdrawal-then-GHS 2/day** is OUR fee, not Paystack's. So we charge rider GHS 2 from withdrawal #2, plus Paystack takes GHS 1 of that.

**Recommendation:** Build a daily batch payout (10am, 1 API call with 100 transfers, GHS 100 in Paystack fees absorbed by Besonc). Make "withdrawal on demand" an explicit premium feature for senior riders.

### Issue 10: Multi-Vendor Single-Customer Is Under-Specified

The plan says multi-vendor orders group with the "10-min threshold" rule. But:

- Each vendor has its own EPT, its own rider handover, its own delivery
- Customer sees one master order; what does "delivered" mean when vendor A's items arrive but vendor B is still 15 minutes away?
- Tip — is it 1 tip split between 2 riders, or 2 tips, or no tip on split?
- Refund — if vendor A delivers wrong item, does the master order's refund include vendor B's full amount too?
- Service fee — does the customer pay 2 service fees or 1?

**Recommendation:** Add a "Multi-vendor order" sub-state machine in Section 4, and a "Master order vs Sub-order" data model. Or: rule that at launch, all multi-vendor orders show 2 separate cart sub-totals and 2 service fees, even if delivered together. This is simpler and more transparent.

### Issue 11: "Group cart with split payment" is post-launch but multi-vendor is in launch

The Sprint Plan puts "Multi-vendor group cart with split payment" in post-launch sprints. But the Service Catalogue has multi-vendor orders (Market mode B = shopping list with multiple market vendors).

Without split payment: customer pays one amount covering all vendors. If one vendor fails, refund = confusing.

**Recommendation:** Either move "multi-vendor split payment" forward, OR explicitly state that Cape Coast launch does not support multi-vendor orders as one cart; each vendor = one order. This is simpler and matches most launch markets.

### Issue 12: Pharmacy Council Licensing

Ghana's Pharmacy Council treats online dispensing of prescriptions as a regulated activity. Our plan treats pharmacy as just "another vendor type with extra verification."

**Recommendation:** Confirm with the Pharmacy Council before launch that Besonc's model (with a licensed pharmacy vendor, prescription upload, pharmacist validation, restricted delivery) is acceptable. If they require a separate license for the platform itself, we need that secured before we can onboard pharmacy vendors.

### Issue 17: "Ledger Not a Wallet" is a Legal Construct, Not a Technical One

The dev plan says (verbatim) the rider earnings record is NOT a wallet. But:
- Riders see "Earnings," "Available," "Pending," "COD Liability" in the app
- They can request withdrawal of GHS 50+
- The system blocks withdrawal based on balance
- To the rider, this is a wallet

Bank of Ghana's "Electronic Money Issuer" (EMI) guidelines and the Payment Systems and Services Act 2019 (Act 987) treat anything that stores value, even if called a "ledger," as a stored-value facility if the user can transact with it. Sources: general Ghana fintech law.

**Recommendation:** Get a legal opinion from a Ghana fintech lawyer before launch. Two possible outcomes:
1. It's fine because Besonc never holds the funds in a customer-accessible way (rider cannot transfer to another rider, only withdraw to their own MoMo)
2. We need to register as an EMI or partner with a licensed EMI

This is not a technical issue. This is a "go/no-go" issue.

### Issue 24: Sprint 1-2 Is Unrealistic

Sprint 1-2 lists:
- API Gateway, Auth, User, 4 BFFs, 13 service skeletons, RabbitMQ + Debezium CDC, Redis + TimescaleDB, observability (Loki/Prometheus/Grafana/Jaeger/Sentry), feature flags (Unleash), shared Flutter packages, CI/CD

That's 12+ weeks of work for a 4-person team, compressed to 4 weeks.

**Recommendation:** Trim Sprint 1-2 to:
- API Gateway
- Auth Service (Hubtel OTP + JWT)
- User Service (basic, no Smile ID yet — add in Sprint 3)
- 1 BFF (Customer)
- PostgreSQL + Redis
- Paystack Charge integration (1 endpoint, mobile_money)
- CI/CD basics

Move observability, feature flags, and 3 of 4 BFFs to Sprint 3-4. The user gets a working login + 1 order end-to-end in 4 weeks, not a half-built platform.

## What I Think is Genuinely Good (Don't Touch)

For balance — these parts of the v3.0 plan are solid:

1. **The 8-service scope** — clean, focused, defensible
2. **The ID formats** (YDC/YDR/YDV/YDO) — clear, future-proof
3. **The two-way ratings** — vendor↔rider, customer↔vendor, customer↔rider
4. **The vendor tier system** (Standard + Premium)
5. **The errand pre-auth + 15% auto-top-up** — this is the right pattern, just needs MoMo reality
6. **The dispatch state machine with countdown trigger** — close to DoorDash's actual model
7. **The data handling SOP** — well-aligned with Ghana Data Protection Act 2012
8. **The Cape Coast-first launch** — discipline about not boiling the ocean
9. **The "no WhatsApp OTP" rule** — clean, reduces vendor lock-in, complies with user instructions
10. **The 5-min countdown trigger for dispatch** — this is the single biggest UX win, don't lose it
